# Conventions — TableTopCafe

Rules for how code in this repo is organized and written. This is the document agents and contributors read at the start of a session. Follow these unless there's a specific reason not to, and if there is, say so in the PR description.

Consistent with [ARCHITECTURE.md](./ARCHITECTURE.md) and [requirements.md](./requirements.md).

## Directory layout

```

    components/
      catalogue/          Public-side components (cards, grid, filters, list view)
      staff/              Staff-side components (forms, tag manager, user admin)
      shared/             Used by both surfaces (buttons, inputs, modals)
    pages/                File-based routes (Nuxt convention)
      index.vue           Public catalogue
      games/[id].vue      Game detail
      staff/              All staff routes; middleware enforces auth
    layouts/
      default.vue         Public layout
      staff.vue           Staff layout

    assets/

  server/

      auth/               Login, logout, session
      bgg/                BGG cache lookup and detail fetch

      queries/            Reusable query functions (see below)
      migrations/         Generated by drizzle-kit; do not hand-edit
      client.ts           Drizzle client instance
    services/             Logic that doesn't belong in a route handler or a query
```

If a file doesn't have an obvious home in this layout, that's a signal to ask before adding a new top-level directory.

## TypeScript

**No `any`, ever.** If a type is genuinely unknown — most commonly, parsing an external API response — use `unknown` and narrow it with a runtime validator (Zod). Casting through `any` to silence the compiler is forbidden; if the type system is in your way, the answer is to model the situation more precisely, not to opt out.

**Inferred types over declared types** for local values and function returns where inference is unambiguous. Declared types at module boundaries (exported functions, route handlers, query functions) so the contract is explicit.

**Schema-driven types.** Drizzle generates TypeScript types from the schema; these are the source of truth for database row shapes. Don't define parallel interfaces for the same data.

**Runtime validation at trust boundaries.** Anything entering the system from outside — request bodies, URL params, BGG API responses, environment variables — is parsed through a Zod schema before being used. Internal function-to-function calls trust their types.

## Database access

**All Drizzle queries live in `server/db/queries/`,** organized by entity (`games.ts`, `tags.ts`, etc.). Route handlers call query functions; they do not build queries inline.

A query function does one logical thing: `getGameById`, `listVisibleGames`, `softDeleteGame`, `mergeTagInto`. If a route handler needs three queries, it calls three functions. If two routes need the same query, they share the function.

**Raw SQL is permitted via Drizzle's `sql` helper** where it's clearer than the builder — particularly for the trigram-based name search. Wrap it in a query function like any other.

**Migrations are generated by `drizzle-kit generate` from schema changes,** never hand-written. To make a schema change: edit the schema file, run `drizzle-kit generate`, review the generated SQL, commit both the schema change and the migration file together. Migrations apply automatically on app container start; never apply them manually in production.

**Audit columns are set in query functions, not in route handlers.** `createGame(input, actorId)` is responsible for setting `created_by` and `created_at`. This keeps audit semantics consistent across all callers.

## Route handlers

**Server routes (`server/api/.../`) are thin.** They (1) parse and validate input with Zod, (2) call one or more query functions or services, (3) shape the response. Business logic that's more than a few lines goes into `server/services/` or a query function.

**Auth is enforced by middleware, not by every handler.** Anything under `server/api/staff/*` and `server/api/admin/*` is behind middleware that verifies the session and (for admin routes) the role. Handlers can trust that `event.context.user` is populated.

**Error responses use Nuxt's `createError`** with a status code and a message. Never leak stack traces or internal errors to the client.

## Components

**One component per file.** File name is the component name in PascalCase: `GameCard.vue`, `TagPicker.vue`.

**Components are organized by surface, not by type.** `components/catalogue/` is everything the public catalogue uses; `components/staff/` is everything the staff interface uses. Components used by both go in `components/shared/`. There is no `components/buttons/` or `components/forms/` — those splits are less useful than they look at this size.

**Props and emits are typed explicitly** with `defineProps<...>()` and `defineEmits<...>()`. No prop-less components reaching into Pinia or global state; pass data in, emit events out.

**Styling uses Tailwind utilities that resolve to design tokens.** Avoid arbitrary values (`text-[#3a3a3a]`, `p-[17px]`) — if a value isn't expressible in tokens, that's a signal the token scale needs to grow, not that this component is special. Component-scoped CSS is acceptable when utilities become unreadable; it still references tokens via `var(--...)`.

**Token utilities for semantic spacing; numeric utilities for sub-grid fine-tuning.** When a spacing value is a design decision — a section gap, card body padding, a major container margin — reference the token explicitly using the generated utility name (`px-md`, `py-lg`, `mb-xl`) or an arbitrary token reference (`p-[--spacing-md]`). When a value is layout fine-tuning — micro-adjustments of ≤12px, sub-pixel rhythm, icon nudges — Tailwind's numeric scale (`py-1.5`, `gap-1`, `p-2.5`) is fine. The test: if a designer reskinned the app, would they expect this value to change? If yes, use the token.

**Shared presentational components own their appearance, not their placement.** A component in `components/shared/` renders its visual identity only — colors, typography, borders, shadow, shape. The parent decides where it is positioned. `FeaturedBadge` is the canonical example: it is a styled pill with no `absolute`, `relative`, or `z-index` inside it; `GameCard` passes `class="absolute top-2 left-2"` to position it over the photo while `GameListItem` passes `class="shrink-0"` to place it inline. The same component renders correctly in both contexts because it does not assume either one.

## Naming

- Files: `kebab-case` for non-component files, `PascalCase.vue` for components.
- Variables and functions: `camelCase`.
- Types and interfaces: `PascalCase`. No `I` prefix.
- Database tables and columns: `snake_case`. Drizzle handles the mapping to camelCase in TypeScript.
- Route segments: `kebab-case` (`/staff/tag-management`, not `/staff/tagManagement`).
- Environment variables: `SCREAMING_SNAKE_CASE`.

## Patterns to prefer

When several approaches would work, prefer:

- **Server rendering over client hydration** for anything that doesn't need to be interactive. Catalogue cards render server-side; the filter sidebar hydrates.
- **A query function over a service** when the operation is "read or write a thing in the database." Services are for logic that spans multiple entities or involves external systems.
- **A composable over a Pinia store** for client-side state that doesn't need to be shared across unrelated components. Pinia is fine when state genuinely needs to be global; most things don't.
- **Explicit imports over auto-magic.** Nuxt's auto-imports are convenient but obscure dependencies; in `server/`, prefer explicit imports so the call graph is greppable.
- **Boring solutions over clever ones.** This codebase will be edited by agents and by future-you with no context. Predictability beats elegance.

## Testing

**Vitest for units and integration:** query functions, services, Zod schemas, anything pure-ish. Tests are co-located with the code they test: `games.ts` and `games.test.ts` sit in the same directory. This is the default for everything in `server/db/queries/`, `server/services/`, and `app/composables/`. The `tests/unit/` directory is reserved for tests that don't have an obvious source file to sit next to — cross-cutting tests, schema validation tests covering multiple files, and so on. If you're writing a test and there's a clear source file for it, co-locate.

**Playwright for end-to-end smoke tests only.** A small handful covering the critical paths: customer loads catalogue and filters, staff logs in and adds a game, admin creates a staff account. Not a full coverage tool; a "did we break something obvious" tool.

**Tests run on every PR via GitHub Actions.** A failing test blocks merge.

## What to do when this document is wrong

If a convention here is actively getting in the way of writing good code for a specific case, the answer is to update the convention, not silently violate it. Raise the case in a PR description; if the convention should change, change it in the same PR.
